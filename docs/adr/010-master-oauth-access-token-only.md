# ADR-010: マスターの認証を OAuth にし、アクセストークンだけをキーチェーンに保存する

## ステータス
承諾済み

## 日付
2026-11-14

## コンテキスト

bswitch は、仮想ユーザーをプロジェクトに参加・除名させるために、それに必要な権限を持つマスターユーザーとして Backlog API を呼ぶ。これまではマスターの API キー (`BSWITCH_MASTER_API_KEY`) を使っていた。

API キーは無期限で、失効させるまで使える。組織によっては API キーの利用が禁止されることもある。1.0.0 では、bswitch の設定ファイル・状態ファイル・環境変数のいずれにも、無期限の認証情報を残さないことを完了基準にしている (#22)。

Backlog の OAuth の仕様は次のとおりである (`docs/api.md`)。

- 認可コードグラントのみ。コードの交換と更新のどちらにもクライアントシークレットが必要
- アクセストークンの有効期間は 3600 秒。リフレッシュトークンの有効期間と失効手段は記載がない

マスターユーザーとしての API 呼び出しは、`switch` / `release` / `status` の実行時に限られ、常時必要なものではない。

### 検討した選択肢

1. **マスターの API キーを使い続ける**
   - 概要: 仮想ユーザーだけを OAuth にし、マスターは API キーのままにする
   - メリット: 実装を変えずに済む。ブラウザでの認可が要らない
   - デメリット: 無期限の認証情報が残り、API キーを禁止する組織では使えない。1.0.0 の目的に反する

2. **アクセストークンとリフレッシュトークンを保存する**
   - 概要: 期限が切れたらリフレッシュトークンで自動更新する
   - メリット: 最初に一度認可すれば、その後ブラウザでの認可が要らない
   - デメリット: リフレッシュトークンの有効期間が記載されておらず、実質的に長期の認証情報を保存することになる

3. **アクセストークンだけを保存する**
   - 概要: アクセストークンを OS のキーチェーンに保存し、期限内は再利用する。期限が切れたらブラウザで認可し直す
   - メリット: 保存される認証情報は最長1時間で無効になる
   - デメリット: 前回の認可から1時間以上たつと、`switch` / `release` のたびにブラウザでの認可が必要になる

4. **毎回ブラウザで認可する**
   - 概要: トークンを保存せず、コマンドを実行するたびに認可する
   - メリット: 認証情報を一切保存しない
   - デメリット: 1時間以内に続けて実行しても毎回認可が必要になり、負担が大きい

## 決定

私たちは **マスターの認証を OAuth にし、アクセストークンだけを OS のキーチェーンに保存する** 方式を使用します (選択肢3)。リフレッシュトークンは保存しません。

あわせて、**期限切れの付与の除名は遅延強制 (`switch` / `release` / `status` の冒頭での除名) だけとし、定期実行用の `enforce` サブコマンドを削除します**。

### 決定理由

- 選択肢1は、API キーをなくすという 1.0.0 の目的そのものに反する
- 選択肢2は便利だが、有効期間の分からないリフレッシュトークンを保存すると、無期限の認証情報を残さないという完了基準を満たせるか判断できない
- 選択肢3でブラウザでの認可が必要になるのは、前回の認可から1時間以上あいて bswitch のコマンドを実行したときだけである。マスターユーザーとしての API 呼び出しはコマンドの実行時に限られるため、この負担は受け入れられると判断した
- 運用してみて負担が大きければ、選択肢2に切り替える

### 認可のしかた

- bswitch は、コマンドの実行中だけ一時的なコールバックサーバー (例: `http://localhost:5034/callback`) を立て、認可コードを受け取ってトークンを取得する。MCP サーバーとは無関係なので、MCP サーバーがローカルでもリモートでも動く
- 開発アプリは、MCP サーバー用とは別に bswitch 用を登録する。開発アプリに登録できる Redirect URI は1つと見られ、MCP サーバーの `/callback` とはポートも異なるためである
- OAuth の処理 (`state` の検証、トークンの取得) は、自前で実装せずライブラリ (Authlib など) に任せる
- クライアント ID とクライアントシークレットは、config に 1Password の参照 (`op://`) で書く

### `enforce` を削除する理由

- これまでは launchd から `enforce` を定期実行し、期限切れの付与を除名できた
- マスターの認可にはブラウザでの操作が必要で、保存したアクセストークンも1時間で切れる。そのため、launchd から無人で実行しても、トークンが切れていれば除名できない
- 動く保証のない定期実行を残すより、bswitch のコマンドを実行したときに必ず行われる遅延強制だけにする

## 結果

### ポジティブ
- マスターについても、無期限の認証情報が設定ファイル・状態ファイル・環境変数に残らない
- API キーを禁止する組織でも bswitch を使える
- `enforce` と launchd の手順がなくなり、セットアップが単純になる

### ネガティブ
- 前回の認可から1時間以上たつと、`switch` / `release` / `status` のたびにブラウザでの認可が必要になる
- 期限切れの付与は、次に bswitch のコマンドを実行するまで除名されず、仮想ユーザーはプロジェクトに所属したままになる (Claude Code からの操作は ADR-009 で `switch` したシェルに限られる)
- マスターの認可がブラウザ操作になるため、E2E テストを自動で実行しにくくなる (方法は #22 で決める)
- bswitch 用の開発アプリの登録が、セットアップの手順に加わる

### トレードオフ
- 1時間ごとの再認可の手間を受け入れる代わりに、長期の認証情報を保存しない
- 期限切れの即時の除名を捨てる代わりに、確実に動く仕組みだけを残す

## コンプライアンス
- リフレッシュトークンを保存しないこと。切り替える場合は、新しい ADR で決定すること
- アクセストークンの保存先は OS のキーチェーンとし、設定ファイル・状態ファイル・環境変数に書かないこと
- クライアント ID とクライアントシークレットは、config に 1Password の参照で書き、値そのものを書かないこと
- コールバックサーバーは、コマンドの実行中だけ立て、`localhost` だけで待ち受けること
- `switch` / `release` / `status` の冒頭で、期限切れの付与を除名すること
