# ADR-007: 作業ディレクトリとBacklogプロジェクトの整合を SessionStart hook のコンテキスト注入で守る

## ステータス
承諾済み

## 日付
2026-07-27

## コンテキスト

ADR-005 / ADR-006 で設計した `bswitch check` は、「現在の `BACKLOG_API_KEY` が state.json の付与記録と一致しているか」だけを判定する。
つまり **キーが壊れていないか** は見ているが、**今の作業内容が正しいプロジェクトに向いているか** は誰も見ていない。

その結果、次の穴が残っていた。

1. 顧客Aのディレクトリで作業中に、別ターミナルで顧客Bのプロファイルへ `switch` する
2. 顧客Aのディレクトリのシェルでは `BACKLOG_API_KEY` が古いまま → `bswitch check` は `MISMATCH` を返すので PreToolUse hook が守る
3. しかし**同じターミナルで `switch` してから元のディレクトリへ戻った場合**、キーと付与記録は一致するため `bswitch check` は `OK` を返す
4. PreToolUse hook（`bswitch_key_guard.sh`）も素通りする
5. AI が顧客Bのプロジェクトへ書き込む

キー整合だけを見る限り、この状態は「正常」である。判定に必要な情報は「今どのディレクトリで作業しているか」であり、`check` はそれを知らない。

さらに、判定のタイミングにも要件がある。Backlog 操作の直前に確認する遅延評価では、Backlog を操作しないセッションでズレに気づけない。
作業ディレクトリと付与中プロジェクトのズレは、ユーザーが作業を始める**前**に気づけることが望ましい。

### 検討した選択肢

1. **ディレクトリ⇔プロファイルの静的マッピングを持つ**
   - 概要: config の `[profile <name>]` に `path` を追加する、またはプロジェクトルートに `.bswitch-profile` マーカーファイルを置き、作業ディレクトリから対応プロファイルを決定論的に引く
   - メリット: 判定が決定論的になり、PreToolUse でのブロック（強制力）まで実装できる
   - デメリット: 全プロジェクト分の対応表を人手で維持するコストが高い。プロファイルが増えるほど設定漏れが起き、漏れたプロジェクトは無警告のまま通る。設定なしで機能しない

2. **`bswitch env` サブコマンド + シェル起動時の環境変数同期**
   - 概要: 現在の付与状態から環境変数を再構成するサブコマンドを追加し、シェル起動時に `eval` して残留キーを解消する
   - メリット: 別ターミナルの残留キー問題そのものを消せる
   - デメリット: 解決対象が「残留キー」であり、本 ADR の課題（ディレクトリとプロジェクトの食い違い）を解決しない。残留キーは既存の PreToolUse hook の deny でカバー済みで、機能追加の価値が薄い

3. **PreToolUse hook へプロジェクト整合判定を追加する**
   - 概要: 既存の `bswitch_key_guard.sh` に、作業ディレクトリと付与中プロジェクトの対応判定を足して deny する
   - メリット: 強制力のあるブロックになる
   - デメリット: 静的マッピング（選択肢1）を持たない以上、bash スクリプトで対応関係を決定論的に判定できない。実装不能

4. **SessionStart hook で現在の付与状態 + 作業ディレクトリをコンテキストへ注入し、AI 自身に判定・報告させる**
   - 概要: セッション開始時に `bswitch check` を実行し、`cwd` と付与中プロジェクトを平文テキストで stdout へ出す。ディレクトリがどの案件のものかは AI がパス・ディレクトリ名・`CLAUDE.md` / `README` から意味的に判断し、判定結果を応答の冒頭に1行で報告する
   - メリット: **設定ファイルの維持が不要**。新しいプロジェクトを追加しても対応表の更新なしで機能する。Backlog を操作しないセッションでもセッション開始時点で警告できる
   - デメリット: `SessionStart` はツール実行をブロックできないため強制力がない。判定は AI の意味的判断に依存するため非決定的

## 決定

私たちは **SessionStart hook で「作業ディレクトリ + 現在の付与状態」をコンテキストへ注入し、整合判定と冒頭1行での報告を AI に行わせる** 設計を採用します（選択肢4）。

あわせて、判定材料として **`bswitch check` の出力へ `project` フィールドを追加**します。

### 決定理由

- 静的マッピング（選択肢1）は決定論的で強制力もあるが、対応表の維持コストが継続的に発生し、設定漏れが「無警告で通る」形で現れる。**設定なしで機能すること**を優先した
- 選択肢3は選択肢1を前提とするため、選択肢1を採らない時点で実装不能
- 選択肢2は解決する問題が本 ADR の課題と異なり、かつ既存 PreToolUse hook で代替されている
- ディレクトリ名と Backlog プロジェクトキーの対応（例: `customer-a` ↔ `CUSTOMER_A`）は表記が揺れるため厳密な文字列規則では判定できないが、意味的な判断は AI が得意とする領域である
- 強制力の欠如は、既存の PreToolUse hook（キー整合の deny）と**役割分担**することで受容できる。キー不整合という決定論的に判定できる事故は引き続きブロックされる

### `bswitch check` への `project` 追加

`Grant` は既に `project` を保持している（`src/bswitch/models.py`）ため、`_handle_check()` の出力辞書へ1行足すだけで足りる。
キー順は `profile` → `project` → `permission` → `status` に固定する。

既存の消費側（`docs/examples/bswitch-statusline.js`・`docs/examples/bswitch_key_guard.sh`）は `profile` / `permission` / `status` しか読まないため後方互換であり、改修は不要。

### 平文 stdout を選んだ理由

Claude Code の `SessionStart` hook は stdout をそのままコンテキストへ追加する。
`hookSpecificOutput.additionalContext` 形式の JSON でも同じことができるが、注入テキストにはバッククォート・絵文字・`<...>` プレースホルダが含まれるため、`jq` での JSON 組み立て時にエスケープ事故を起こしやすい。
平文 stdout なら bash の引用付き heredoc（`<<'EOF'`）でシェル展開もろとも止められるため、文面を1文字も変えずに出力できる。

### 注入テキストの設計

- 判定は **Backlog を操作するかどうかに関わらず、セッション開始時に1回**行わせる。遅延評価にすると Backlog を操作しないセッションでズレに気づけない
- 報告は**応答の冒頭に1行**に限定する。通常作業のノイズにしないため
- `status` が `OK` 以外の場合は、プロジェクト対応の判定より**キー不整合の報告を優先**させる。キーが壊れている状態では、そもそも付与記録どおりの権限で動いていない
- 対応が読み取れない場合は「判断できません」（❓）と報告させ、黙って進ませない
- **全プロファイル一覧（`bswitch list` 相当）は注入しない。** プロファイルが多い環境では毎セッション全プロジェクトキーがコンテキストに載る。判断には付与中の1〜2件で足りる
- `source`（`startup` / `resume` / `clear` / `compact` / `fork`）でフィルタしない。コンパクション後は文脈が失われるため再注入が有効

## 結果

### ポジティブ
- 設定ファイルの維持なしで、ディレクトリと付与中プロジェクトの食い違いに気づけるようになった
- Backlog を操作しないセッションでも、作業開始前に警告が出る
- `bswitch check` に `project` が入ったことで、消費側（hook・ステータスライン）が付与先プロジェクトを表示できるようになった
- 付与0件かつ `BACKLOG_API_KEY` 未設定のときは完全に無音なので、Backlog と無関係なプロジェクトでの作業にノイズが出ない

### ネガティブ
- **`SessionStart` はツール実行をブロックできない**（公式ドキュメントに `Can block? No` と明記）。本機能は注意喚起であり、強制力は既存の PreToolUse hook（キー整合のみ）に留まる
- 注入されるのは指示であって強制ではないため、判定・報告そのものが実行されない可能性がある。文面で「最初の応答で必ず」と明示して実行率を上げるが、100% にはならない
- ディレクトリと Backlog プロジェクトの対応判定が非決定的である。ディレクトリ名から案件が読み取れない構成では ❓（判断不能）が続く
- セッション途中で別ターミナルが `switch` しても `SessionStart` は再発火しないため、そのズレは検知できない
- 毎セッション開始時に `bswitch check` が1回走る（ADR-006 でフィンガープリント比較に変えたため `op read` は発生せず、1Password 認証ダイアログは出ない）

### トレードオフ
- 決定論的な判定と強制力を捨てる代わりに、設定ファイルの維持コストゼロと「全プロジェクトで自動的に機能する」性質を得た
- 対応表がないため誤検知（対応しているのに ❓）も起こり得るが、黙って通すより安全側に倒している

## コンプライアンス
- `bswitch check` の出力キー順は `profile` → `project` → `permission` → `status` とすること
- `check` は引き続き Backlog API を呼ばず、`BSWITCH_MASTER_API_KEY` を要求せず、出力先は stderr とすること（ADR-005 の軽量コマンド分類を維持）
- SessionStart hook は **stdout へ平文テキスト**を出し、stderr へは何も出さないこと
- SessionStart hook は全プロファイル一覧を注入してはならない。注入するのは付与中のグラントのみとすること
- SessionStart hook は API キーの値を出力してはならない
- SessionStart hook は fail-open とすること（`bswitch` 未導入 / `check` の異常終了 / JSON 以外の出力 → 無音で `exit 0`）
- 付与0件かつ `BACKLOG_API_KEY` 未設定のときは何も出力しないこと
- 強制力を持つブロックは PreToolUse hook（`bswitch_key_guard.sh`）が担い、SessionStart hook にブロックを期待しないこと
