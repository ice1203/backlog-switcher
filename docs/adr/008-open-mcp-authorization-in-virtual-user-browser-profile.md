# ADR-008: MCP の認可画面を、付与中の仮想ユーザーの Chrome プロファイルで開く

## ステータス
承諾済み

## 日付
2026-11-14

## コンテキスト

1.0.0 では、仮想ユーザーの API キーを使わず、Backlog 公式の MCP サーバーを OAuth モード (HTTP) で動かし、Claude Code の `/mcp` から仮想ユーザーとして認可する (#22)。

Backlog の OAuth にはスコープがなく、トークンは認可したユーザーの権限をすべて持つ。したがって「どのユーザーで認可するか」が、AI が操作できる範囲をそのまま決める。

一方で、次の事情がある。

- Claude Code は MCP の認可画面を既定のブラウザで開く。既定のブラウザには、仮想ユーザーではないユーザー (マスターユーザーなど) がログインしていることが多い
- そのまま「許可」を押すと、MCP サーバーはそのユーザーとして認可され、AI が仮想ユーザーより広い権限で Backlog を操作できてしまう
- 公式の MCP サーバーには、認可できるユーザーを制限する設定がない
- Claude Code は、起動時の環境変数 `BROWSER` にコマンドが指定されていれば、そのコマンドで認可画面を開く (公式ドキュメントに記載はなく、実機で確認した)

### 検討した選択肢

1. **利用者が認可画面の URL を、仮想ユーザーのプロファイルに手で貼る**
   - 概要: 既定のブラウザで開いた URL をコピーし、仮想ユーザーでログインした Chrome プロファイルで開き直す
   - メリット: bswitch の実装が要らない
   - デメリット: 認可画面は自動で既定のブラウザに開くため、そのまま「許可」を押す誤操作を防げない。誤ると、気づかないまま仮想ユーザー以外のユーザーとして認可される

2. **MCP サーバー側で、認可できるユーザーを制限する**
   - 概要: 認可したユーザーが仮想ユーザーでなければ、MCP サーバーが拒否する
   - メリット: どのブラウザで開いても、仮想ユーザー以外での認可を確実に防げる
   - デメリット: 公式の MCP サーバーにその機能がなく、実現するにはフォークして保守する必要がある。リモートの MCP サーバーでは手を入れられない

3. **`bswitch switch` が、そのシェルに `BROWSER` を出力する**
   - 概要: `switch` のたびに、付与した仮想ユーザーのプロファイルで開くコマンドを `BROWSER` に設定する
   - メリット: 付与と同時にブラウザが決まり、付与の記録を読み直す必要がない
   - デメリット: `switch` を実行していないシェルでは `BROWSER` がなく、既定のブラウザで開いてしまう。安全側に倒れない

4. **`BROWSER` を Claude Code の設定に固定し、bswitch のコマンドが付与の記録を見て振り分ける**
   - 概要: `~/.claude/settings.json` の `env` に `BROWSER=bswitch-open-browser` を固定で設定する。`bswitch-open-browser` は `state.json` から期限内の付与を読み、その権限の仮想ユーザーの Chrome プロファイルで開く。付与がないときは Backlog と MCP サーバーの URL を開かない
   - メリット: どのシェルから起動しても同じ動きになる。付与がないときは開かないため、安全側に倒れる
   - デメリット: `BROWSER` の扱いが公式ドキュメントにない挙動に依存する。`BROWSER` は Claude Code の子プロセスにも引き継がれる

## 決定

私たちは **`BROWSER` を Claude Code の設定に固定し、bswitch 同梱の `bswitch-open-browser` が付与の記録を見て認可画面を振り分ける** 方式を使用します (選択肢4)。

### 決定理由

- 守りたいのは「仮想ユーザー以外で認可させないこと」であり、そのためには、付与がない・設定を忘れたといった状態で、既定のブラウザに開かないことが必要である。選択肢3は `switch` を実行していないシェルで既定のブラウザに開くため、この要件を満たさない
- 選択肢2は最も確実だが、公式の MCP サーバーに機能がなく、bswitch が MCP サーバーに依存しない方針 (#22) にも反する
- 選択肢1は誤操作をそのまま許す
- 付与の記録 (`state.json`) は bswitch がすでに持っており、`check` と同じ内部処理で読めるため、追加の状態を持たずに済む

### コマンドの形

- `bswitch-open-browser` は、`pyproject.toml` の `[project.scripts]` に、`bswitch` と並ぶ別のコマンド名として追加する。サブコマンド (`bswitch open-browser`) にしないのは、Claude Code が `BROWSER` の値をスペースで区切って扱うかが不明で、`bswitch open-browser` が1つのコマンド名として探される可能性があるためである
- 振り分けの対象は、config の `space` (Backlog スペース) のホストと、`mcp_url` (MCP サーバーの接続先 URL) のスキーム・ホスト・ポートに一致する URL とする。MCP サーバーの `/authorize` は Backlog の認可画面へリダイレクトするため、MCP サーバーの URL も仮想ユーザーのプロファイルで開く必要がある
- それ以外の URL は既定のブラウザで開く。`gh` の Web 認証など、Claude Code の子プロセスが `BROWSER` を使う場合に影響を出さないためである

## 結果

### ポジティブ
- 付与がない状態では Backlog と MCP サーバーの認可画面が開かず、仮想ユーザー以外で認可される経路を塞げる
- `switch` したシェルかどうかに関わらず、認可画面は付与中の仮想ユーザーのプロファイルで開く
- MCP サーバーに手を入れないため、公式の MCP サーバーでもリモートの MCP サーバーでも同じ仕組みで使える

### ネガティブ
- Claude Code が `BROWSER` で認可画面を開くことは公式ドキュメントに記載がなく、Claude Code の更新で変わる可能性がある
- 認可画面の URL を手で既定のブラウザに貼れば、仮想ユーザー以外で認可できてしまう。手作業までは防げない (#23)
- Chrome のプロファイルに依存する。仮想ユーザーごとに Chrome プロファイルを作り、ログインしておく必要がある
- `BROWSER` を見る子プロセスはすべて `bswitch-open-browser` を通る

### トレードオフ
- MCP サーバー側での確実な制限 (選択肢2) を捨て、手元のブラウザの選択で防ぐ。その代わりに、MCP サーバーに依存しない仕組みにできる

## コンプライアンス
- `bswitch-open-browser` は、期限内の付与がないとき、Backlog スペースと MCP サーバーの URL を開かずにエラーで終了すること
- 仮想ユーザーは付与の `permission` から決めること (read → reader、write / admin → writer)。Chrome プロファイルは config の `reader_browser_profile` / `writer_browser_profile` から取ること
- 付与の記録の読み込みは `check` と同じ内部処理を使い、Backlog API を呼ばないこと
- Backlog スペースと MCP サーバー以外の URL は、既定のブラウザで開くこと
- `bswitch switch` は `BROWSER` を出力しないこと。`BROWSER` は Claude Code の `settings.json` の `env` に固定で設定する
