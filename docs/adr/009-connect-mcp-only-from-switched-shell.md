# ADR-009: `bswitch switch` したシェルの Claude Code だけを MCP サーバーにつなぐ

## ステータス
承諾済み

## 日付
2026-11-14

## コンテキスト

API キー方式では、`bswitch switch` が `BACKLOG_API_KEY` をそのシェルに設定していた。環境変数はシェルごとにあるため、`switch` していない新しいターミナルには権限がなく、そこで起動した AI は Backlog を操作できなかった。

1.0.0 で Backlog MCP サーバーを OAuth モードで使うと (#22)、この性質がなくなる。

- MCP サーバーは Mac に1つだけ動き、認可した仮想ユーザーのトークンを1つ持つ。どのターミナルから接続しても、同じトークンで操作する
- Claude Code は MCP の認証情報をターミナルごとではなく利用者単位で保存し、新しいセッションもそれを使って接続する
- Backlog のプロジェクトへの所属はスペース全体の設定で、ターミナルとは関係がない

その結果、新しいターミナルで起動した Claude Code も、最後に認可した仮想ユーザーとして、所属中のプロジェクトをそのまま操作できる。防ぎたいのは、意図せずプロジェクトに所属したままの状態で、AI がそのプロジェクトを操作してしまうことである。

Backlog の所属がスペース全体の設定である以上、権限そのものをターミナルごとに分けることはできない。そこで、「`bswitch switch` を実行していないシェルでは、Claude Code が MCP サーバーにつながらない」状態を目指した。

### 検討した選択肢

1. **PreToolUse hook で、MCP のツールを呼ぶたびに確認する**
   - 概要: `switch` がシェルに印となる環境変数を出力し、hook が `mcp__backlog-oauth__*` の呼び出しのたびに、印・付与の期限・引数のプロジェクトを確認して止める
   - メリット: 付与していないプロジェクトへの操作も、その場で止められる
   - デメリット: ツールを呼ぶたびに確認が走り、回りくどい。ツールごとに引数の形が違い、hook の保守が重い。hook を入れ忘れると守られない

2. **`switch` で MCP サーバーを起動し、`release` で止める**
   - 概要: 付与があるときだけ MCP サーバーを動かす。MCP サーバーはトークンをメモリにしか持たないため、止めると認可も消える
   - メリット: 付与がなければ、どのターミナルからも操作できない
   - デメリット: ターミナルごとの区別はできない。`switch` のたびに認証し直す必要がある。リモートの MCP サーバーでは使えない

3. **MCP サーバーの起動時間を制限する**
   - 概要: 起動から決まった時間、または付与の期限で、MCP サーバーを止める
   - メリット: 期限切れのまま操作できる時間を短くできる
   - デメリット: 動いているあいだは、新しいターミナルからも操作できる。目的のターミナルごとの区別にならない

4. **bswitch 経由で Claude Code を起動し、付与があるときだけ MCP の設定を渡す**
   - 概要: `claude --mcp-config` で、起動時に MCP サーバーの設定を渡す
   - メリット: 普通に起動した Claude Code には MCP サーバーがない
   - デメリット: Claude Code の起動のしかたが変わる

5. **MCP サーバーの接続先 URL を環境変数で登録する**
   - 概要: Claude Code に MCP サーバーを `'${BSWITCH_MCP_URL}'` という URL で登録し、`bswitch switch` がそのシェルに `BSWITCH_MCP_URL` を設定する。Claude Code は起動するたびに、起動したシェルの環境変数で `${...}` を置き換える
   - メリット: hook も起動方法の変更も要らない。`switch` していないシェルでは URL が置き換わらず、MCP サーバーにつながらない
   - デメリット: 環境変数の置き換えは、公式ドキュメントでは `.mcp.json` についてしか書かれていない

## 決定

私たちは **MCP サーバーの接続先 URL を環境変数 `BSWITCH_MCP_URL` で登録し、`bswitch switch` がそのシェルに設定する** 方式を使用します (選択肢5)。

### 決定理由

- 目的は「`switch` していないシェルでは操作できない」ことであり、選択肢2と3はターミナルごとの区別にならない
- 選択肢1は目的を満たすが、ツールの呼び出しごとの確認は仕組みとして重く、保守の負担が大きい
- 選択肢4は目的を満たすが、利用者に Claude Code の起動方法の変更を求めることになる
- 選択肢5は、API キー方式と同じ「シェルの環境変数で権限の有無が決まる」性質を、Claude Code の既存の機能だけで取り戻せる
- ユーザースコープ (`~/.claude.json`) の登録でも置き換わることは、実機で確認した。変数がないシェルで起動すると `'url' is not a valid URL` で接続に失敗し、変数を設定したシェルではつながる

## 結果

### ポジティブ
- `bswitch switch` を実行していないターミナルで起動した Claude Code からは、Backlog MCP のツールを使えない
- hook や起動方法の変更が要らず、`switch` の出力に1つ変数を足すだけで済む
- config の `mcp_url` を変えれば、リモートの MCP サーバーでも同じ仕組みで使える

### ネガティブ
- 防げるのは Claude Code から MCP サーバーを使う操作だけである。Backlog の所属はスペース全体で残る
- `switch` したシェルでは、付与の期限が切れても `release` / `restore` を実行するまで `BSWITCH_MCP_URL` が残る。期限切れの除名は、次に bswitch を実行したときに行われる (ADR-010)
- ユーザースコープでの置き換えは公式ドキュメントに明記がなく、Claude Code の更新で変わる可能性がある

### トレードオフ
- ツールの呼び出しごとの確実な確認 (選択肢1) を捨て、起動したシェルの環境変数で接続の有無を決める。その代わりに、仕組みを単純に保てる

## コンプライアンス
- Claude Code への登録は、URL をシングルクォートで囲んで `'${BSWITCH_MCP_URL}'` とすること。囲まないと、登録した時点でシェルが変数を展開してしまう
- 登録する URL に既定値 (`${BSWITCH_MCP_URL:-...}`) を付けないこと。付けると、`switch` していないシェルでもつながる
- `bswitch switch` と、期限内の付与があるときの `restore` は、`BSWITCH_MCP_URL` を出力すること。値は config の `mcp_url` (MCP サーバーの接続先 URL。既定値は `http://localhost:3333/mcp`) をそのまま使う。リモートの MCP サーバーは接続先のパスが `/mcp` とは限らないため、パスを bswitch で組み立てない
- `release` と、期限内の付与がないときの `restore` は、`BSWITCH_MCP_URL` を unset すること
